# t3-profile v3 usage

Status: usage display requirements agreed on and implementation plan reviewed
on 2026-08-19.

`t3-profile list` must show usage for every registered profile. Usage checks
are for `t3-profile` profiles only and must run in the selected profile's
validated provider environment.

## `list` output

Append a `USAGE` column to the existing `PROVIDER NAME SHARING HOME` profile
list. Keep the current headings, provider/name sort, display-path behavior, and
empty-registry behavior:

```text
PROVIDER  NAME  SHARING   HOME                                      USAGE
claude    bets  standard  ~/.t3-profile/profiles/claude/bets        5h 100% · resets Aug 19, 12:59 PM America/Chicago
                                                                    week 45% · resets Aug 24, 2:59 PM America/Chicago
codex     work  isolated  ~/.t3-profile/profiles/codex/work         week 65% · resets Aug 20, 8:59 AM America/Chicago
```

The output must:

- include every registered profile, whether or not its usage check succeeds;
- preserve the existing provider/name ordering and all existing columns;
- show Claude's five-hour and weekly usage windows in `5h`, then `week` order;
- show only Codex's weekly usage window;
- show reset times with an IANA timezone;
- keep continuation lines aligned at the exact start of the `USAGE` column;
  and
- render failed or unavailable usage without failing, hiding, or removing the
  profile row.

A complete profile or provider failure renders as:

```text
claude    bets  standard  ~/.t3-profile/profiles/claude/bets        unavailable
```

A single failed Claude window keeps its label and preserves the successful
window:

```text
claude    bets  standard  ~/.t3-profile/profiles/claude/bets        5h unavailable
                                                                    week 45% · resets Aug 24, 2:59 PM America/Chicago
```

An invalid percentage or reset timestamp makes the entire affected window
unavailable. Do not print individual `percent unavailable` or
`resets unavailable` fragments.

## Profile selection and validation

Usage retrieval is part of `t3-profile list` and must use the same registry and
profile-scoped environment rules as `auth`, `run`, and `doctor`.

For every registry entry:

1. Compute the expected identity with `pathsFor` from the resolved managed
   root, provider, name, and registered source home.
2. Require the registry `profileHome` and `instanceId` to match that expected
   identity.
3. Call `validateManagedProfileChain({ managedRoot, provider, name,
   requireHome: true })`.
4. Use the returned canonical profile home when building the provider
   environment.

A missing, redirected, outside-root, mismatched, or otherwise invalid managed
profile home makes only that profile's usage `unavailable`. Do not start a
provider process for an invalid profile. Managed-root and registry read or
parse failures remain fatal because the profile list itself cannot be trusted.

## Exact provider usage retrieval

### Claude

Read the selected managed profile's OAuth access token from its regular
`.credentials.json` file at the canonical profile home. Do not read a
different profile, follow a redirected credentials file, print the token, or
refresh it.

Fetch the Anthropic OAuth usage endpoint:

```text
GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <claudeAiOauth.accessToken>
anthropic-beta: oauth-2025-04-20
```

The JSON response contains typed usage windows:

```text
five_hour.utilization       numeric percentage, 0 through 100
five_hour.resets_at         ISO-8601 timestamp
seven_day.utilization       numeric percentage, 0 through 100
seven_day.resets_at         ISO-8601 timestamp
```

Normalize `five_hour` to `five_hour` and `seven_day` to `week`. A missing or
invalid individual window keeps its label and becomes unavailable; credential,
HTTP, timeout, oversized response, invalid JSON, or unsupported response
failures make the complete Claude usage check unavailable. Do not parse the
human-formatted `.result` returned by `claude -p "/usage" --output-format json`.
That CLI envelope is not a stable machine-readable usage contract.

### Codex

For each Codex profile, spawn a fresh, independent app-server with the
profile-scoped environment:

```text
codex app-server
```

Use `makeEnvironment("codex", canonicalProfileHome)` for the child, which sets
`CODEX_HOME` to the canonical managed home. Do not attach to the existing T3
app-server, use its MCP endpoint, or invoke login, logout, token-refresh, or
rate-limit-reset operations.

The default stdio transport is newline-delimited JSON-RPC. Add a dedicated
bidirectional stdio helper; `inspectCommand` cannot drive the app-server
because its stdin is ignored. Use this sequence:

1. Send `initialize` with request ID `0` and `clientInfo` name/title
   `t3-profile`. Use the package `VERSION` for `clientInfo.version` rather than
   a hard-coded v3 string.
2. Read until the response with ID `0` arrives and require a successful
   `result`.
3. Send the `initialized` notification.
4. Send `account/rateLimits/read` with request ID `1`.
5. Read until the response with ID `1` arrives and require a successful
   `result`.
6. Close stdin and terminate the app-server through the bounded cleanup path.

Match responses by ID rather than arrival order. Ignore notifications and
responses for unrelated IDs while waiting. A malformed or oversized JSONL
line, duplicate required response, JSON-RPC error, premature EOF, missing
required result, or write failure makes the usage check unavailable.

Apply the existing five-second inspection deadline from process start through
the rate-limit response. Capture at most 65,536 bytes from stdout and stderr
independently, and reject any line or stream that exceeds its bound. On every
success, error, EOF, and timeout path:

- close the child's stdin;
- request normal termination;
- escalate to `SIGKILL` after the existing termination grace period;
- destroy the pipes; and
- await child closure before settling.

No app-server process may remain after its usage check completes.

Select the Codex bucket in this order:

1. `result.rateLimitsByLimitId.codex`, when it is a valid object;
2. otherwise `result.rateLimits`, only when it is a valid object and its
   `limitId` is missing or equals `codex`.

Do not select a differently named bucket. The relevant window fields are:

```text
usedPercent         current percentage used
windowDurationMins  duration of the quota window
resetsAt            Unix epoch timestamp in seconds
```

`primary` and `secondary` are positions, not semantic window names. Inspect
both non-null values and identify the weekly window by
`windowDurationMins === 10080`. Do not relabel an arbitrary `primary` window
as `week`; the official protocol examples include non-weekly primary windows.
For v3, ignore other valid durations and render only the single weekly window.
If there is no weekly window, more than one weekly candidate, or the weekly
candidate has invalid required fields, render the Codex profile as
`unavailable`. A `secondary: null` value only means that no secondary window
was returned; do not invent one.

Convert `resetsAt` from epoch seconds into the invocation's display timezone.
The official transport, handshake, endpoint, bucket, and field definitions are
documented in the [Codex App Server documentation](https://learn.chatgpt.com/docs/app-server).

The fresh profile-scoped app-server approach was validated with
`CODEX_HOME=~/.t3-profile/profiles/codex/main`. The observed response contained
a 10,080-minute primary window at 65% with no secondary window. This observation
is a fixture, not a guarantee that `primary` always means `week`.

## Provider usage model and formatting

Use a common internal model so provider-specific responses do not leak into
the list renderer:

```text
profile: provider + name
displayTimezone: IANA timezone
windows:
  - id: five_hour | week
    status: available
    percent: number
    resetsAt: timestamp
  - id: five_hour | week
    status: unavailable
```

Capture one display timezone for the entire `list` invocation with
`Intl.DateTimeFormat().resolvedOptions().timeZone`. This honors a valid
process-local timezone, including `TZ`. If the result is absent or invalid,
use `UTC` and display `UTC`; never silently format in UTC while labeling
another timezone.

A valid percentage must be a finite number from 0 through 100 inclusive.
Render it with `Math.round`. A valid reset value must produce a finite date.
Format with an explicit `en-US` `Intl.DateTimeFormat`, the invocation timezone,
and these components:

```text
MMM D, h:mm AM/PM Area/Location
```

Example:

```text
Aug 19, 12:59 PM America/Chicago
```

Do not include a weekday, year, seconds, or timezone abbreviation.

## Collection, isolation, and provider state

Collect profiles independently with at most four provider checks active at
once. Render only after collection completes so provider timing cannot change
the existing provider/name sort.

Every per-profile identity, filesystem, binary, transport, timeout, parse,
normalization, or formatting failure must be caught independently. Return
normalized unavailable data and continue. Never place raw provider errors,
stdout, stderr, JSON-RPC messages, environment values, credentials, bearer
tokens, or stack traces in list output.

Usage collection is read-only from `t3-profile`'s control-plane perspective:
it must not write the registry or T3 settings, change the caller's environment,
prompt for authentication, or explicitly request login, logout, credential
refresh, or quota reset. Native provider processes may still perform their
normal authenticated-read maintenance, including provider-owned cache, log,
or token handling. Do not claim that launching a native provider process
prevents all provider-owned filesystem writes.

## Codex and T3 app-server context

The main Codex instance is authenticated through `t3-profile`. The working T3
topology is:

```text
t3 serve
  └─ codex app-server
       └─ http://127.0.0.1:3773/mcp
          bearer token from T3_MCP_BEARER_TOKEN
```

Usage collection always uses the fresh profile-scoped app-server described
above. It does not attach to this existing process or endpoint. Any existing
T3 bearer token is process-local and must not appear in diagnostics or list
output.

## Failure and exit behavior

Usage is supplementary list data. A failed usage check must:

- produce `unavailable` rather than an error stack or provider diagnostic;
- leave the affected profile in the list;
- allow all remaining profiles and usage checks to complete;
- leave no provider child running; and
- preserve the normal successful `list` exit behavior.

Only a failure to resolve the managed root or read and validate the registry
changes the normal `list` exit behavior. Do not treat unavailable usage as zero
usage, an expired window, or a missing profile.
