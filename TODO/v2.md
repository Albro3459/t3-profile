# t3-profile v2 candidates

These features are explicitly deferred. V1 implementation should not build abstractions for them unless a small v1 boundary naturally requires one.

## `doctor`

Diagnose provider binaries, authentication status, profile-home permissions, link integrity, T3 registration, version compatibility, and Windows link capability.

## `sync`

Compare the registry with T3 settings, show a dry-run change set, and repair safe drift. Consider authenticated online T3 settings RPC only when its versioning and secret-redaction contract are suitable for an external CLI.

## Running-T3 detection

Detect T3 Code, `t3 serve`, and `t3 connect` before settings mutation. Refuse safely and report what the user needs to stop. Never terminate processes automatically.

## Custom sharing

Offer resource-by-resource selection after standard and isolated behavior is proven. Claude can use a direct allowlist. Codex needs an explicit product decision because current T3 shadow homes share broad state and do not support a custom link allowlist while preserving the primary continuation group.

## `remove`

Safely remove a managed profile, its owned links, registry entry, and T3 provider instance. Require an explicit confirmation, preserve the source primary home and all unmanaged files, and clearly explain that native credentials may remain in the provider's own credential store unless the user separately chooses to revoke them.
